# 프론트엔드 설계 — EV 충전 최적 시간 추천

2026-09-21 · 대상: `frontend/` · 근거: 화면 디자인 PDF 27장, 노션 [기능 명세서](https://app.notion.com/p/3e2c8fd1afc981d0a00ef5fdcec314f1) · [API 명세서](https://app.notion.com/p/3e2c8fd1afc981b38befc694478b0e72)

## 무엇을 만드는가

충전 조건을 넣으면 가장 싼 시간을 알려주는 반응형 웹. 디자인 PDF는 모바일 13화면과
데스크톱 12화면을 모두 그려 두었다. F-07 주변 충전소만 빼고 전부 붙었다.

| 화면 | 경로 | 쓰는 API | 상태 |
| --- | --- | --- | --- |
| 홈 | `/` | 없음 (정적) | 구현 |
| 충전 조건 입력 | `/recommend` | `GET /api/me/vehicles` | 구현 |
| 추천 결과 | `/recommend/result` | `POST /api/recommend`, `GET /api/timeline`, `POST /api/me/plans` | 구현 |
| 하루 단가 | `/timeline` | `GET /api/timeline` | 구현 |
| 로그인·회원가입 | `/login` `/signup` | `/api/auth/*` | 구현 |
| 마이페이지 | `/me` | `GET /api/me`, `DELETE /api/me` | 구현 |
| 내 차량 | `/me/vehicles` | `/api/me/vehicles` | 구현 |
| 충전 기록 | `/me/plans` | `/api/me/plans` | 구현 |
| 즐겨찾는 충전소 | `/me/favorites` | `GET /api/me/favorites` | 구현 |
| 주변 충전소 | `/stations` | `GET /api/chargers` | 구현 (서비스키 필요) |

백엔드가 아직 501인 기능(F-09 태양광, F-10 자연어 질의)은 계약대로 UI를 만들어 두고,
501이 오면 그 사실을 화면에 적는다. 가짜 데이터를 채우지 않는다.

주변 충전소는 서비스키가 `backend/.env`에 있어야 뜬다. 없으면 501이 오고 화면이
"준비 중"으로 표시한다 — 코드 문제가 아니다.

## 스택

Next.js 16 (App Router) · React 19 · TypeScript · Tailwind v4 · Vitest + Testing Library.
노션 기술 스택 문서가 Next.js(반응형 웹, PWA)로 정해 둔 것을 따른다.

## 확정한 결정

### 1. 백엔드는 rewrite로 넘긴다

백엔드 `main.py`에 CORS 미들웨어가 없고, 인증이 httpOnly 쿠키다. 브라우저가
`localhost:3000 → :8000`을 직접 치면 교차 출처라 둘 다 걸린다.

`next.config.ts`의 rewrites로 `/api/*`와 `/health`를 넘기면 브라우저 입장에선
동일 출처다. 쿠키가 손대지 않아도 실리고, **백엔드 코드를 건드릴 필요가 없다** —
지금 백엔드는 `review-notion-ev-charge` 브랜치에 있고 main에 없다.

백엔드 주소는 `BACKEND_URL` 환경변수로 바꾼다 (기본 `http://localhost:8000`).

### 2. 시각은 Date를 거치지 않는다

백엔드는 시각을 항상 `+09:00`을 달아 보내고, 표준시 없는 입력을 KST로 읽는다
(API 명세서 1장). 프론트에서 `new Date(...)`로 만들어 `toLocaleString`에 넘기면
브라우저 표준시로 다시 읽힌다. 심사위원 노트북이 어느 표준시든 "22:00 추천"은
22:00으로 보여야 한다.

그래서 `lib/format.ts`의 `parseKstWallClock`이 ISO 문자열에 적힌 벽시계 값을
정규식으로 그대로 꺼낸다. 요청을 만들 때도 `toISOString()`을 쓰지 않는다 —
UTC로 바뀌어 9시간 어긋난 추천이 돌아온다.

### 3. 충전 조건은 URL 쿼리로 넘긴다

입력 화면과 결과 화면이 서로 다른 라우트다. 조건을 전역 상태에 두면 결과 화면에서
새로고침하는 순간 빈 화면이 된다. URL에 실으면 새로고침·뒤로가기·링크 공유가
공짜로 따라오고, 시연에서 링크 하나로 특정 추천을 바로 띄울 수 있다.

쿼리 이름은 백엔드 요청 필드와 똑같이 쓴다 (`battery_kwh`, `soc_now`, …) —
URL만 보고도 무슨 요청이 나갈지 안다. 계약은 `lib/recommend-params.ts`에
테스트로 고정되어 있다.

### 4. 차트는 직접 그린다

디자인이 구체적이다. 시간별 부하구간 색, 막대 위에 겹치는 두 줄 마커(추천 · 지금 바로),
둥근 상단, 그리고 축이 24시간(하루 단가)과 14시간(추천 결과, 18시→다음날 08시)
두 가지다. 차트 라이브러리로 이걸 맞추는 게 직접 그리는 것보다 길다.

`components/chart/PriceBarChart.tsx` 하나를 두 화면이 공유한다. 컬럼 배열을
통째로 받으므로 축이 0시에서 시작하지 않아도 된다.

**막대 높이는 0을 바닥으로 단가에 비례한다.** 축을 자르면 62.5원과 125.1원이
몇 배 차이처럼 보인다 — 절감액을 주장하는 화면에서 그건 과장이다.

### 5. 로그인 여부는 한 곳에서만 판단한다

세션이 httpOnly 쿠키라 자바스크립트가 읽을 수 없다. "로그인했나?"를 아는 유일한
방법은 `GET /api/me`를 불러 401인지 보는 것이다. 화면마다 이걸 하면 같은 요청이
네 번 나가고 로딩 처리가 제각각이 된다. `SessionProvider` 하나가 판단한다.

상태를 넷으로 나눴다. `loading`을 따로 둬야 로그인한 사용자에게 "로그인" 버튼이
번쩍이지 않고, `unreachable`을 손님과 구분해야 백엔드가 꺼졌을 때 "로그인하세요"로
오도하지 않는다 — 그 경우 사용자는 로그인을 시도하고 또 실패한다.

**401만 손님이다.** 처음엔 `status === 0`(fetch 자체 실패)만 연결 실패로 봤는데,
rewrite 프록시를 쓰면 브라우저 fetch는 성공하고 프록시가 500 + 평문을 돌려준다.
백엔드를 실제로 꺼 보고서야 발견했다. 지금은 401이 아닌 모든 실패를 연결 실패로 보고,
`detail`을 읽을 수 있는 5xx만 백엔드가 살아서 낸 오류로 취급한다.

### 6. 급속/완속은 출력으로 가른다

충전기 `type`은 코드(`"02"`·`"04"`)이고 속도를 결정하지 못한다 — 실데이터에서
`type=04`가 7~350 kW에 걸쳐 있고 그중 137대가 50 kW 미만이다. 타입으로 가르면
수백 대가 틀리고, 틀리면 사용자가 완속에 세워놓고 급속인 줄 안다.

`capacity_kw`로 가른다. API가 주는 실측값이라 넘겨짚을 여지가 없다. 경계 50 kW는
실데이터에 41~49 kW가 한 대도 없어서 고른 값이지만, 그건 지금 데이터의 성질이지
영원한 법칙이 아니다. 그래서 **기준을 화면에 적는다.**

0 kW인 충전기가 20대 있다. 완속이라 말하지 않고 "출력 정보 없음"으로 둔다.

타입 코드는 화면에 띄우지 않는다. `stat`과 갈리는 지점은 **대체할 더 나은 필드가
있느냐**다 — `stat`은 원문 말고 줄 게 없어 원문이라도 보여주는 게 낫고, 타입이
답하려던 질문에는 `capacity_kw`가 더 정확히 답하므로 코드는 숫자만 남는다.

### 7. 충전 기록의 월은 충전 날짜 기준이다

시안의 카드가 `10월 7일 (수) · 22:00 – 01:00`, `10월 10일 (토) · 11:00 – 14:00`인데
날짜가 충전 구간과 정확히 맞물린다 — 저장일로는 설명이 안 된다. 사용자가 묻는 것도
"10월에 얼마나 아끼나"이지 "9월에 계획을 몇 번 세웠나"가 아니다.

백엔드와 합의해 `saved_plans.charge_start`(= `result.best.start`)를 기준으로
**표시·필터·정렬을 모두** 맞췄다. 자정을 넘는 구간은 시작일에 한 번만 잡힌다.
저장일(`created_at`)은 보조 정보로 남긴다 — "언제 세운 계획인지"도 알아야 한다.

이 전환에서 기준을 따라오지 못한 두 곳이 드러났고, 통합 검증에서만 잡혔다.
월 선택이 과거만 줘서 방금 저장한 다음 달 계획을 고를 수 없었고, 빈 화면이
"아직 저장한 계획이 없어요"라고 해서 다른 달에 있는 계획을 없는 것처럼 말했다.

### 8. `vehicle_id`는 저장 요청에만 싣는다

차량을 고르면 그 사실이 URL에 실려 결과 화면까지 간다. 저장할 때 `vehicle_id`를
보내야 `SavedPlan.vehicle_name`이 채워지고, 그래야 기록이 "어느 차로 세운 계획인지"를 안다.

**추천 요청에는 싣지 않는다.** `vehicle_id`가 붙은 요청은 로그인을 요구해서, 결과 URL을
공유받은 게스트가 401을 맞는다. 이 앱은 로그인 없이 쓸 수 있는 게 전제다. 차량을 고르면
값(배터리·출력·모드)이 이미 폼에 복사되므로 추천 결과는 동일하다.

기록 목록은 차량 이름과 조건을 **둘 다** 보여준다. 차량을 고른 뒤 값을 고쳐 저장할 수 있는데,
이름만 보여주면 그 차의 제원 그대로 계산됐다고 오해한다.

### 색만으로 정보를 주지 않는다

부하구간 팔레트를 검증한 결과: 색맹 분리는 통과(ΔE 12.5 protan / 15.7 tritan),
**대비는 두 색이 3:1 아래다** (중간부하 2.95:1, 주말 할인 1.5:1). 디자인 확정색이라
바꾸지 않되, 같은 정보를 글자가 함께 나른다.

- 범례가 차트와 항상 같이 있다
- 막대마다 `aria-label`로 "18시 · 최대 · 132.0원/kWh"가 읽힌다
- 같은 데이터가 숨은 `<table>`로도 들어 있다
- 하루 단가 화면은 밴드별 단가 목록을 화면에 직접 띄운다

잡아주지 못한다.

## 오류 처리

FastAPI는 오류를 두 모양으로 보낸다 (API 명세서 1장). 업무 오류는 `detail`이 문자열,
필드 검증 실패는 배열이다. 화면마다 이 분기를 풀면 같은 코드가 네 군데 생기므로
`lib/api/client.ts`의 `messageFromDetail`이 한 곳에서 문장으로 만든다.

`ApiError`는 `status`와 함께 `notImplemented`(501)·`needsLogin`(401)·`unreachable`을
노출한다. `unreachable`은 "서버의 답이 아니라 서버에 닿지 못했다"는 뜻이다 — fetch 자체가
터진 경우와, rewrite 프록시가 업스트림 실패로 돌려준 `detail` 없는 5xx가 여기 든다.
둘 다 "백엔드가 실행 중인지 확인하세요"로 바꿔 준다. 원래 메시지("fetch failed",
"Internal Server Error")는 사용자에게 아무것도 알려주지 않는다.

## 요금이 잠정치라는 사실을 숨기지 않는다

`tariff.yaml`의 값은 한전 공식 요금표 확보 전의 잠정치고, 백엔드가 응답마다
`unverified_tariff_items`를 실어 보낸다. 프론트는 이 배열이 비어 있지 않으면
**항상** 고지 배너를 띄운다. 조건부로 숨기면 잠정 금액이 확정 금액처럼 보인다.

`assumptions` 배열("충전 출력 일정 · 연속 충전 · 기본요금 제외")도 결과 화면에 적는다.

## 테스트

순수 함수는 TDD로 먼저 쓴다 — `format`, `charging`, `recommend-params`,
`api/client`. 컴포넌트는 렌더 + 핵심 상호작용, `fetch`는 `vi.stubGlobal`로 모킹한다.

절대 금액을 단언하지 않는다. 요금표가 확정되면 전부 바뀐다. 대신 불변식을 본다 —
막대 높이가 단가에 비례하는가, 할인 없는 날에 할인 배너가 안 뜨는가,
목표 충전량이 현재보다 낮으면 요청이 안 나가는가.

## 남은 공백

- **충전기 상태 코드 매핑** — 확정 전이다. 공식 활용가이드가 없고, 실데이터에
  코드표에 없는 `9`가 5.3%(1,734대) 있다. 모르는 코드는 **원문 그대로** 보여주고
